# 公共组件复用与治理

## 1. 盘点方法

在开始抽象前：
- 搜索组件定义和引用。
- 找到使用页面、使用次数和业务场景。
- 对比 Props、slots、事件、状态和样式覆盖。
- 识别是否已有相似组件或重复实现。
- 记录组件与页面、变体、状态之间的影响关系。

## 2. 组件分层

| 层级 | 职责 | 示例 |
|---|---|---|
| 基础组件 | 最小交互和视觉单元 | Button、Input、Select、Tag、Icon |
| 通用业务组件 | 多页面可复用的完整交互模式 | PageHeader、SearchFilter、DataTable、Modal、Drawer、Tabs |
| 复合组件 | 多个基础/业务组件组合成领域模块 | 领域卡片、数据面板、详情面板 |
| 页面专属组件 | 单一页面的特定业务表达 | 专属流程图、复杂业务配置面板 |

## 3. 抽象决策

适合抽象：多个页面重复出现、结构和交互基本一致、变更可以统一获益。

不适合抽象：仅一个页面使用、业务规则高度特殊、抽象后需要大量条件分支、Props/slots 难以理解。

优先升级已有组件；通过 variants、slots、配置和组合支持合理差异。不要为了复用把所有页面强行做成同一种布局。

## 4. 组件质量要求

- 单一职责，命名清楚，接口稳定。
- Props 默认值合理，事件语义一致。
- 支持必要状态：default / hover / focus / active / disabled / loading / error。
- 尺寸、间距和颜色使用 Design Tokens。
- 有合理的键盘操作和可访问名称。
- 不把业务 API 或页面路由硬编码进纯 UI 组件。
- 不为极少数特例引入难以维护的万能 Props。

## 5. 视觉一致性与变体

复用的目标是稳定的交互和视觉语言，而不是让每个页面看起来完全相同。允许页面模式根据任务密度、用户角色和内容类型呈现差异，但应共享基础 Token、交互规则和组件质量标准。

## 6. 公共组件改造的回归要求

建立“组件 → 引用页面 → 变体/状态”的影响矩阵。改造后至少覆盖主要引用页面、不同变体、窄屏、长内容和关键交互。无法覆盖全部页面时，明确抽样范围和剩余风险。

## 7. 推荐交付记录

记录组件名称、原实现位置、使用页面、改造内容、新增变体、受影响页面、测试结果和后续维护信息（如项目有要求）。模板见 [../templates/component-audit.md](../templates/component-audit.md)。
