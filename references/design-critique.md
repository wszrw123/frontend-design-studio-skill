# 设计评审与迭代规范

本文件定义 Image 设计稿进入前端编码之前必须通过的设计质量门禁。评审对象是设计方案，不是已经实现的代码。

## 1. 评审目标

判断设计是否：
- 正确解决用户需求和业务任务。
- 具备清晰的信息架构、视觉焦点和阅读路径。
- 有符合产品定位的视觉识别度，而非无差别模板。
- 在排版、色彩、组件、图标和背景资产上保持一致。
- 延续用户已确认认可的视觉语言，不无理由推翻有效区域。
- 覆盖真实交互、数据状态和响应式布局。
- 能在当前工程约束下实现，并满足可访问性和性能要求。
- 关键用户任务路径清楚，操作成本没有因视觉改造而增加；需要减负时不会牺牲功能可发现性和业务安全。

## 2. 独立视角的证据式评审

优先让与设计生成者分离的评审角色/Agent 审查已生成的设计。评审者应先阅读业务目标、真实页面、数据状态和验收标准，再看目标设计稿，不继承生成者的自评分或“已经完成”结论。

如果没有实际可用的独立评审 Agent，执行单独的反向审查轮次：假设初稿存在明显缺陷，尝试找出可观察的反证；明确标记“单 Agent 反向审查”，不得谎称有第三方或多个 Agent 评审。

每条 Major/Blocker 需记录：截图区域/组件 → 可观察证据 → 用户影响 → 修订动作 → 复评结果。主观审美判断应当明确其性质，不能编造自动测量结果。

至少比较正常态和一个高风险数据状态，例如缺失数据、真实零值、密集多列、长文案或窄屏布局；不能只评审漂亮的理想示例。

## 3. 评审流程

1. 重新阅读需求简报和不可变业务约束。
2. 将设计稿与现状截图/需求结构逐项对照。
3. 按下方量表评分，并为每个低分项记录证据。
4. 将问题分为 Blocker、Major、Minor。
5. 给出明确修订动作：改信息结构、改层级、改构图、改字体/颜色、改资产或补状态。
6. 修订 Image 提示词或参考图，重新生成必要部分。
7. 对修订稿复评；关键门禁通过后才允许开始编码。
8. 记录真实采用的评审方式、初稿和修订稿路径、已接受的设计取舍及浏览器阶段待验证假设。

不得把第一张生成图直接视为最终稿。不要为了评分而无限生成；问题已解决、关键门禁通过且剩余取舍合理时即可进入实现。

## 4. 设计质量量表

采用 0–4 分，只作为诊断工具：

- 0：缺失或与需求冲突。
- 1：明显不足，影响用户完成任务。
- 2：基本可用，但存在清晰可改进点。
- 3：质量良好，符合成熟产品预期。
- 4：表现突出，细节和整体性均有说服力。

| 维度 | 评审问题 |
|---|---|
| 需求与业务准确性 | 用户任务、关键字段、功能入口和业务约束是否完整保留？ |
| 信息架构 | 内容分组、导航层级和操作路径是否自然？ |
| 视觉层级与密度 | 首要信息是否突出？是否过空、过挤或平均用力？ |
| 品牌识别与设计个性 | 是否契合产品定位？是否只是通用模板换色？ |
| 排版与布局 | 字体层级、行高、对齐、栅格、间距和留白是否协调？ |
| 色彩与表面 | 主辅色、状态色、背景、边框、圆角和阴影是否克制统一？ |
| 组件一致性 | 相同功能是否使用一致模式？是否存在卡片堆叠或样式漂移？ |
| 视觉资产质量 | 图标、插画、背景是否相关、统一、清晰且有必要？ |
| 交互与状态 | 点击反馈、焦点、禁用、加载、空、错误和成功状态是否覆盖？ |
| 响应式 | 不同视口是否有合理重排，而不是机械缩放？ |
| 可访问性 | 文字对比、焦点、语义、触控区域和阅读性是否合格？ |
| 工程可实现性 | 是否符合现有技术栈、组件能力、数据和性能约束？ |
| 内容与状态适应性 | 真实零值、缺失、极端数值、长内容和布局压力是否被考虑？ |
| 视觉语言连续性 | 是否合理保留用户认可的区域和品牌语言，而非无理由重做？ |
| 任务效率与可发现性 | 关键任务是否易于完成？减少步骤是否仍让核心功能容易找到？ |
| 验收可追溯性 | 是否存在可复现的视口、数据状态、目标图和差异验收方式？ |

## 5. 门禁规则

必须满足：
- 需求与业务准确性不得低于 3。
- 信息架构、视觉层级、可读性和工程可实现性不得低于 2；目标为 3 或以上。
- 如果任务涉及移动端，响应式维度不得低于 2。
- 如果设计使用视觉资产，资产质量与语义不得低于 2。
- 不得存在 Blocker 级问题。
- 对 Major 必须修复、明确接受为取舍或记录为未通过；不能用“整体不错”掩盖。
- 核心真实数据状态和目标视口必须有可落地策略，不能全部留给编码阶段临时处理。
- 对已有产品，明确哪些满意区域需要保护；对交互优化，不能隐藏核心功能或跳过必要业务安全措施。

任何关键维度不通过时，先迭代设计稿，不得开始正式编码。若用户明确接受某项取舍，记录原因和影响后可继续，但不能隐瞒风险。

## 6. 问题严重级别

### Blocker
- 删除或隐藏关键业务功能。
- 信息架构导致用户无法找到主要任务。
- 文字或控件不可读、关键数据表达错误。
- 使用虚构业务数据误导用户。
- 设计与现有工程约束根本冲突。
- 核心交互没有可实现路径。

### Major
- 视觉焦点不清、信息密度明显失衡。
- 品牌感缺失或套用无差别模板。
- 关键组件样式不一致。
- 重要状态或移动端布局缺失。
- 图标、插画或背景素材明显不合适。
- 对比度、焦点或触控体验存在明显问题。

### Minor
- 局部间距、字重、圆角、阴影或图标尺寸微调。
- 非关键装饰细节不一致。
- 不影响任务的次要布局优化。

## 7. 迭代策略

一次只处理一组有因果关系的问题：
- 信息架构问题：先调整内容分组和操作路径。
- 视觉层级问题：调整焦点、字号、对比、密度和留白。
- 品牌识别问题：重新定义视觉方向、色彩比例和视觉母题。
- 资产问题：重做统一图标组、插画或背景资产。
- 响应式问题：为不同视口重新规划布局和组件行为。
- 可实现性问题：将复杂视觉简化为真实组件、CSS、SVG 和可维护布局。
- 操作成本问题：重新组织输入、默认值、复用和渐进披露，同时复核功能可发现性、撤销/确认和错误恢复。

不要仅通过增加渐变、阴影、卡片、背景图或动画来修复设计问题。

优先查找上游根因：需求和数据 → 信息架构 → 视觉方向 → 组件与资产 → CSS 实现。目标是修复问题，而不是机械增加生成轮数。

## 8. 评审报告

记录：
- 设计稿版本/路径和目标视口。
- 评审维度及分数。
- Blocker / Major / Minor 问题。
- 问题的视觉证据和用户影响。
- 修订动作及重新生成的版本。
- 最终门禁结论：PASS / REVISE / BLOCKED。
- 用户确认的取舍（如有）。
- 评审方式（独立 Agent / 人工 / 单 Agent 反向审查，如实填写）、真实证据以及后续浏览器验收路径。
