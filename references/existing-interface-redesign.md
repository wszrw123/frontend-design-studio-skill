# 已有界面改造工作流

## 1. 需求理解（必须是第一步）

先从用户输入、已有对话、产品说明和当前任务中提取：
- 目标页面和目标用户。
- 当前最影响体验的问题及优先级。
- 用户希望保留、调整、删除或新增的内容。
- 关键业务操作和不可改变的行为。
- 交付范围：单页面、相似页面、公共组件或整个模块。
- 目标终端和验收标准。
- 真实内容数据契约与边界状态：零、未知、缺失、超长文本、加载失败、密集数据等。

若需求足够明确，直接进入下一步，不重复询问。若一个关键缺失会导致设计方向完全不同，只提出一个最关键的澄清问题。

## 2. 现状截图与源码分析

- 使用真实登录态和真实路由获取截图；如果只能使用用户截图，标明截图覆盖范围。
- 截图应覆盖首屏、关键内容区、页面底部、弹窗、Tab 切换和重要状态。
- 记录视口大小、滚动位置、数据状态和截图时间。
- 阅读页面源码，识别实际 DOM 结构、组件来源、样式覆盖、接口和权限约束。
- 记录信息层级、密度、对齐、留白、颜色、字体、图标、背景、可点击区域、响应式和交互问题。
- 对页面中的异常状态进行区分：真实产品 UI、浏览器检查器覆盖层、调试浮层、系统提示和临时遮罩。
- 留存不含检查器覆盖层的原始截图，记录视口、内容状态、缩放、滚动位置；作为 Before 证据。

## 3. 视觉方向定义

根据产品定位、品牌规范、用户角色、业务任务和内容密度确定视觉方向。明确：
- 核心视觉焦点和首要任务。
- 视觉语言：色彩比例、排版、表面、图标和图像风格。
- 信息密度与页面节奏。
- 应保留的产品识别特征，以及需要改变的旧设计模式。

不要默认套用某一种 SaaS 模板，也不要为了“设计感”添加无关装饰。

## 4. Image 重设计

将原页面截图作为图像参考输入，并附上已确认的需求、必须保留的功能和目标视口。要求生成完整页面高保真方案，而不是只生成氛围图。

复杂页面按需要补充：
- 首屏与完整页面。
- 重要弹窗、Tab、详情区和操作状态。
- 移动端独立构图。
- 必要的图标、插画和背景资产。

## 5. 设计评审门禁

按照 [design-critique.md](design-critique.md) 对设计稿进行独立评审。必须检查业务准确性、信息架构、视觉层级、品牌识别、排版、资产、交互、响应式、可访问性和工程可实现性。

关键问题未修复前不得进入编码。评审优先由独立角色完成，不具备条件时明确采用反向审查。记录具体视觉证据、修订方案、压力内容状态和最终设计稿路径。

## 6. 设计拆解与实施

把通过评审的设计稿拆成页面布局、Design Tokens、公共组件、页面专属组件、视觉资产、交互状态和响应式规则。先盘点组件和资产，再决定复用、升级、生成或新建。

## 7. 三图差异与回归范围

必须按 [visual-diff.md](visual-diff.md) 对齐 Before（原真实截图）、Target（评审通过的设计稿）、After（代码运行截图）。当差异源自设计缺陷时要重新评审设计，不能直接用 CSS 硬贴不合理的构图；当差异源自工程实现时修复代码。多视口与数据压力检查见 [state-driven-layout.md](state-driven-layout.md)。

## 8. 回归范围

任何公共组件变更都必须检索所有引用页面。至少覆盖：
- 默认态与主要变体。
- 长标题、长内容和窄视口。
- Loading、Empty、Error、Disabled、Focus 等状态（如组件支持）。
- 弹窗/抽屉的打开、关闭、滚动和底部操作。
- Tab 切换、筛选、分页和表单交互。

## 9. 不允许的捷径

- 不理解业务就直接让 Image 生成。
- 只根据截图猜代码结构而不检查现有实现。
- 不评审第一张 Image 设计稿就开始编码。
- 把设计稿当背景图片铺在页面上。
- 只改当前页面却忽略公共组件影响。
- 将浏览器检查器高亮覆盖层误认为产品 UI。
- 仅通过构建成功就宣布视觉验收通过。
- 忽略真实空数据、长内容和窄视口导致的层级失衡。
- 在没有 Target/After 截图的情况下声称实现已经和设计稿一致。
