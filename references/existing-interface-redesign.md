# 已有界面改造工作流

## 1. 需求理解（必须是第一步）

先从用户输入、已有对话、产品说明和当前任务中提取：
- 目标页面和目标用户。
- 当前最影响体验的问题及优先级。
- 用户希望保留、调整、删除或新增的内容。
- 关键业务操作和不可改变的行为。
- 交付范围：单页面、相似页面、公共组件或整个模块。
- 目标终端和验收标准。

若需求足够明确，直接进入下一步，不重复询问。若一个关键缺失会导致设计方向完全不同，只提出一个最关键的澄清问题。

## 2. 现状截图与页面分析

- 使用真实登录态和真实路由获取截图；如果只能使用用户截图，标明截图覆盖范围。
- 截图应覆盖首屏、关键内容区、页面底部、弹窗、Tab 切换和重要状态。
- 记录视口大小、滚动位置、数据状态和截图时间。
- 阅读页面源码，识别实际 DOM 结构、组件来源、样式覆盖、接口和权限约束。
- 记录问题：信息层级、密度、对齐、留白、颜色、字体、图标、背景、可点击区域、响应式和交互。

## 3. Image 重设计

将原页面截图作为图像参考输入，并附上已确认的需求、必须保留的功能和目标视口。要求生成完整页面高保真方案，而不是只生成装饰图。

建议设计说明包含：
- 页面类型、用户角色和首要任务。
- 现状问题与改造目标。
- 必须保留的模块和功能入口。
- 期望的视觉方向与品牌约束。
- 内容密度、数据量和目标视口。
- 图标、插画、背景图的素材策略。

## 4. 设计拆解与实施

把设计稿拆成页面布局、设计 Token、公共组件、页面专属组件、视觉资产、交互状态和响应式规则。先处理公共组件和基础样式，再处理页面专属内容，减少重复实现。

## 5. 回归范围

任何公共组件变更都必须检索所有引用页面。至少覆盖：
- 默认态与主要变体。
- 长标题、长内容和窄视口。
- Loading、Empty、Error、Disabled 等状态（如组件支持）。
- 弹窗/抽屉的打开、关闭、滚动和底部操作。
- Tab 切换、筛选、分页和表单交互。

## 6. 不允许的捷径

- 不理解业务就直接让 Image 生成。
- 只根据截图猜代码结构而不检查现有实现。
- 把设计稿当背景图片铺在页面上。
- 只改当前页面却忽略公共组件影响。
- 仅通过构建成功就宣布视觉验收通过。
